# rdp_timing v39 — スパンの一部の画素だけ Z で落ちるとき（ゲームの重なり）のコスト

v33〜v38 で、ゲームのリストの三角形が合成三角形より 10〜20% 高い理由は、形・大きさ・順序・配置・テクスチャの向き・シザー外では
ないことが分かりました。合成で残っている違いは **Z の落ち方** です。合成は「全画素が通る」か「全画素が落ちる」（v33: 全部落ちると
1 スパン 27〜54 clk 安い）しか測っておらず、ares はその 2 つのテーブルを通過率で線形に混ぜています。ゲームでは重なりのために
**スパンの中の一部の画素だけが落ちる**のが普通で、実機がそのスパンを「通ったスパン」並みに扱う（メモリアクセスがブロック単位なら）か
「落ちた分だけ安く」するかで、ゲームのリストの見積もりが 10% 変わります。これを直接測ります。

- BAR の 2 サイクルモード（0x182c0f / 0x0c182078）と DK64 の 1 サイクル（0x882c0f / 0x00552078）、0F 三角形、1 三角形 8 スパン
  （`bar_h1_*` は 1 スパン）、幅 4 / 8 / 13 / 32 / 64、ランダム配置、320 幅、VI オフ、8 MB。
- Z バッファのプリセット（各 run の前に CPU で書く）: `pass`（全部遠い）/ `fail`（全部近い）/ `px1`（奇数列が近い: 1 画素おき）/
  `px2` `px4` `px8` `px16` `px32`（2 / 4 / 8 / 16 / 32 列ごとに交互）/ `rows`（奇数行が近い: スパン単位で半分落ちる）/
  `rand50` `rand25` `rand75`（画素ごとに乱数で 50 / 25 / 75% が近い）/ `blk8_50`（8 画素ブロック単位で乱数 50%）。
- `Y` 行の形式は v31〜v35 と同じ（clk/スパン、clk/三角形）。`ares_reference.txt` = ares series v10（ares はパターンに依らず同じ値:
  合成では通過率 1 と推定するため）。`python3 compare.py 実機ファイル` で、各パターンの実機の値が pass（0）と fail（1）の間の
  どこにあるかを出します。線形なら px*/rand50/rows は 0.5、rand25 は 0.25、rand75 は 0.75。実機で約 3 分。
