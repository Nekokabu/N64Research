# rdp_timing v38 — ゲームのリストの三角形を描く順番だけ変えて再生（隣接三角形の相互作用）

v37 まででゲームのリストの実機/ares（series v10）は全体で ±7%、三角形の形（傾き・垂直化・画素への吸着・大きさ）を変えても
差の付き方は変わらず、「ゲームのリストが合成リストより 10〜20% 高い」原因は三角形 1 個ずつの性質にはありませんでした。
残る候補は **三角形どうしの関係**（連続する三角形が同じ画素・同じメモリ行に触る、描画順序）です。v38 は三角形の中身を一切変えず、
ステート命令の間に連続する三角形の並び（run）の順番だけを変えます。ares のモデルは順序に無関係（Z の合否が変わる分だけ動く）なので、
実機/ares が variant で動けばそれが順序（隣接）依存のコストです。VI オフ、8 MB、実機で約 2 分。

- リスト: `bar_2316`、`bar_i2274`、`bar_i2314`、`dk64_797`、`dk64_d6373`、`mgc_p4_4316`、`mgc_p2_1802`（v37 と同じ）
- variant: full / tri_only、`tri_reverse`（各 run を逆順）、`tri_interleave`（偶数番目を先に、奇数番目を後に: 隣どうしが離れる）、
  `tri_sorty`（run 内を上端の行で昇順に）、`tri_firsthalf` / `tri_secondhalf`（run の前半 / 後半だけ残し、残りは NOP）、
  `tri_every2`（1 個おきに残す: 隣接する三角形の重なりがほぼ消える）。
  run は 744 個を超えると分割して並べ替えます（ゲームのリストでは滅多にない）。
- `X` 行の形式は v22〜v37 と同じ。`ares_reference.txt` = ares series v10。`compare.py 実機ファイル v10`（`v38runs/v10.txt` に置く）。

見方: tri_reverse / interleave / sorty の実機の値が full と同じなら順序依存は無し。firsthalf + secondhalf ≈ full、every2 ≈ full/2 から
外れる分（実機）が、隣接する三角形の重なり・連続性に付いているコストです。
