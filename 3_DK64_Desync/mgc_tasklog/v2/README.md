# mgc_tasklog v2 — パート 1〜3 の実機フレームタイムライン（2 本）

v1（`mgc_tasklog.z64`）はパート 4 の頭から記録し、パート 4・5・RETRO ロゴ（「@」が出る直前のフレーム 2233 まで）を取りました。
ares series v10 はこの区間で **パート 4 −3.8%、パート 5 −3.5%、ロゴ +0.8%**、「@」の時点で実機より 129 VI（2.2 秒）早く、
これが「Retroactive の横の @ と音のカンが合わない」正体です（実機では @ と同時に鳴ります: 録画 156.70 s）。
series v11（パッチ 0015: スパン幅を 4 サブスキャンラインの和集合に）で −1.7% / −2.0% / +1.9%、「@」は +5 VI（0.08 秒）になりましたが、
**パート 1〜3 の実機の記録が無い**ので（パート 4 の頭で ares は v10 −13 VI、v11 +58 VI）、残りの合わせ込みにパート 1〜3 のログが要ります。
96 KB のバッファには約 2300 フレームしか入らないので 3 本に分けます（v1 はパート 4 の頭〜ロゴのフレーム 2233 = 「@」の 6 フレーム前まで）。

- `mgc_tasklog_a.z64`（`hook_a.S`: MIN_VI 0）: **最初のグラフィックタスクから**記録（パート 1 全部 + パート 2 のほぼ全部、約 60 秒で止まる）
- `mgc_tasklog_b.z64`（`hook_b.S`: MIN_VI 3000）: **パート 2 → 3 のロードの切れ目**（VI 3000 以降で 3.8 VI 以上あいた最初のタスク）から記録
  （パート 3 全部 + パート 4 の大半。v1 のログとパート 4 の頭で重なるので、3 本をつなげて全体のタイムラインになります）

- `mgc_tasklog_c.z64`（`hook_c.S`: MIN_VI 8500、END_VI 11200）: **パート 5 → RETRO ロゴのロードの切れ目**（VI 8500 以降で 3.8 VI 以上あいた最初の
  タスク = 実機 VI 9023）から記録し、ロゴ・「@」（VI ≈9393）・フェード・MGC のポスター・その先まで、**VI 11200（約 3 分 7 秒）で SRAM に書いて止まります**
  （バッファは埋まりません: ares では 1808 フレーム・14351 件）。v1 の終わり（フレーム 2233）と 2 フレーム重なります。

## 手順（v1 と同じ）
1. `python3 make_patch.py mgc_2011.z64 hook_a.bin mgc_tasklog_a.z64`、同じく `hook_b.bin` → `mgc_tasklog_b.z64`、`hook_c.bin` → `mgc_tasklog_c.z64`
2. SD に入れて起動（セーブタイプ SRAM 768K。256K しか無ければ最初の 32 KB = 約 780 フレーム分だけ残ります）。
   a は約 1 分、b は約 2 分、c は約 3 分 7 秒（ポスターが出てしばらく後）で画面が止まります。止まったらリセット → メニューに戻ってセーブデータ（`mgc_tasklog_a.srm` / `_b.srm`）を送ってください。
   ROM ごとに電源を入れ直して（途中で止まった状態からの再起動は不可）。
3. 解析: `python3 decode_tasklog.py mgc_tasklog_a.srm`（形式は v1 と同じ、マジック `MGTL`、version 7）。

`ares_v12_c_frames.txt` は c の ares（series v12）のログ（記録開始 VI 9017、「@」の後 VI 9482 からポスター、1 VI のフレームが続く）。
`ares_v10_a_frames.txt` / `ares_v10_b_frames.txt` は series v10 のハーネスの同じログ（a: 最初のタスクが VI 10、パート 1 → 2 の切れ目が
フレーム 1232（VI 1387 → 1421、34 VI）。b: 記録開始 VI 3568、パート 3 → 4 の切れ目がフレーム 1345（VI 5746 → 5751））。
実機の録画では パート 1 → 2 の黒い区間が 102 フレーム（22.96〜24.67 s）あり、ares の 34 VI より長く見えます — ロードが遅いのか、
フェードアウトを描いているのかを a のログで切り分けます。
